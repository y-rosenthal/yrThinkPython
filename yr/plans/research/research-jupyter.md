# research:jupyter

I checked these facts from source code and by running things. The test runs used nbclient on IPython 9.17.1 and on IPython 7.34.0 with ipykernel 6.17.1 (close to Colab), real JupyterLab 4.6.4 and Notebook 7.6.3 servers driven by headless Chromium, and two small Jupyter Book builds made with the repo's _config.yml.

**Q1: JupyterLab, Notebook 7, VS Code**
- **Collapse marker:** a collapsed heading is saved per cell as `jp-MarkdownHeadingCollapsed: true`. The notebook opens with that section's cells hidden.
- **Run All:** it runs the hidden cells, and they stay hidden afterwards, outputs included.
- **The raises-exception tag:** Run All honors it.
  - JupyterLab: PR #6424 (fixes #2412) shipped it in 1.0; PR #7020 (closes #7015) fixed a regression in 1.1.
  - Notebook 7, classic Notebook 6.5 and the VS Code Jupyter extension honor it too.
  - Untagged cells stop Run All; tagged cells let it continue.
- **Caught errors:** a run_code cell that catches the error and calls showtraceback() returns status 'ok', and Run All continues with no tag needed.
- **Catch 1, Shift+Enter:** in JupyterLab, pressing Shift+Enter on a collapsed Answer heading moves into the hidden section and expands it. A student stepping through the page opens each answer that way. Arrow keys skip the section.
- **Catch 2, VS Code:** it ignores the collapse marker and keeps folding as editor state, so the answers open expanded there.

**Q2: how errors look**
- **SyntaxError:** exec plus showtraceback shows the same source line, caret and message as a normal cell. It differs only in the 'File <string>:3' header and a line number one higher, caused by the newline after the opening triple quotes.
- **Runtime errors, IPython 9:** showtraceback() shows the run_code frame, and tb_offset does not remove it.
- **Runtime errors, IPython 7.34:** the frame is hidden by default, but no source lines are shown.
- **Normal-looking errors:** calling `get_ipython().run_cell(code, store_history=False)` inside run_code makes errors look exactly like a normal cell's on both IPython versions, with status 'ok'. Two quirks:
  - On IPython 8 and later the label reads 'Cell In[N+1]'.
  - It swallows KeyboardInterrupt, so pressing Stop would not halt Run All. run_code should re-raise it.

**Q3: the website (myst-nb)**
- **Answer headings:** every markdown heading goes into the right-hand table of contents, so '#### Answer' would add 'Answer' entries with anchors #answer, #id1, #id2. myst-nb ignores the collapse marker, so on the site the heading is plain and the code cell is visible.
- **No spanning:** each markdown cell is parsed on its own, so a dropdown cannot span cells. If you try, it breaks silently, with no warning.
- **Tags:** hide-cell, hide-input and hide-output give collapsed toggles whose labels can be changed per cell (`mystnb.code_prompt_show`). Tags on markdown cells do nothing except remove-cell.
- **What prep_notebooks.py must do:**
  - Fold the Answer heading and the cells after it into the existing single dropdown cell (or turn the heading into a rubric or bold text).
  - Keep the heading exactly one level below the question, or the build gives a new myst.header warning.
- **No outputs on the site:** review pages are not executed for the website, so an answer code cell there would show no output.

**Q4: a custom cell magic**
- **Storing:** a magic registered with register_cell_magic stores the cell body as text even when it has a syntax error, and runs nothing. Running it later through nested run_cell gives normal-looking errors.
- **Run order:** if a magic cell runs before the setup cell, it gives a UsageError and stops Run All.
- **Changes the repo would need:**
  - prep_notebooks.py must strip the `%%` line, as it already does for %%expect.
  - check_notebooks.py rejects unknown magics, so the new name must be added to KNOWN_MAGICS.
- **Still unknown:** whether Colab's editor underlines errors inside a magic cell.

**Colab, from file evidence only:** Colab saves collapsed sections in `metadata.colab.collapsed_sections` as a list of heading cell ids. To ship pages collapsed in both Colab and JupyterLab, the notebooks would probably need both markers. I haven't tested this in Colab.

## Findings

- **Q1-a** [verified]: JupyterLab 4 and Notebook 7 save a collapsed heading as the markdown cell metadata key "jp-MarkdownHeadingCollapsed": true. The key is set when the heading is collapsed, deleted when it is expanded, and read when the notebook loads. When the notebook opens, every cell below that heading is hidden, up to the next heading of the same or a higher level. Nested sections are handled.
  - Evidence: Source: jupyterlab v4.6.4 packages/cells/src/widget.ts:152 `const MARKDOWN_HEADING_COLLAPSED = 'jp-MarkdownHeadingCollapsed'`. On main (4.7.0a2) the same code is at line 156 (read on load at ~2198, setter at ~2294-2302). The collapse loop is NotebookActions.setHeadingCollapse in packages/notebook/src/actions.tsx. Run in headless Chromium against a real JupyterLab 4.6.4 and Notebook 7.6.3 server: a notebook whose '### Answer' cells carried that key opened with the code and markdown cells under each Answer hidden and a '+ N cells hidden' button showing. Output: scratchpad/ultra/jupyter-facts/browser/lab_test_output.txt, nb7_test_output.txt, tagged.ipynb.runall.png.
  - Impact: An '#### Answer' heading saved with this key opens collapsed, together with its code cell, in JupyterLab and Notebook 7. The button shows only how many cells are hidden (1 vs 2), not their content.
- **Q1-b** [verified]: Run All runs every cell inside a collapsed heading. After it finishes, those cells and their outputs (prints, errors) stay hidden. When the notebook's last cell was itself inside a collapsed section, Run All did not expand that section either.
  - Evidence: Headless Chromium against JupyterLab 4.6.4 and Notebook 7.6.3, command notebook:run-all-cells. The hidden cells got execution counts 2, 3 and 4 with outputs and stayed hidden:true. Files: browser/lab_test_output.txt, lab_test3_output.txt (last cell inside a collapsed section: still hidden after Run All), nb7_test_output.txt, screenshots tagged.ipynb.runall.png and lastcell.runall.png. Source: runAll passes all of notebook.widgets to Private.runCells (actions.tsx).
  - Impact: In JupyterLab and Notebook 7, the 'Answer heading section' layout meets the professor's goals 1-3 (Run All reaches the end, no answer is visible afterwards, the answer opens when clicked). This holds as long as no cell raises, or raising cells are tagged or caught.
- **Q1-c** [verified]: JupyterLab, Notebook 7, classic Notebook 6.5 and VS Code all honor the raises-exception tag during Run All. For a tagged cell, JupyterLab sends execute_request with stop_on_error=false, so the kernel does not abort the queued cells.
  - Evidence: JupyterLab v4.6.4 packages/outputarea/src/widget.ts:984 (OutputArea.execute sets stopOnError=false when metadata.tags includes 'raises-exception'). Added by JupyterLab PR #6424 'Allow Raises-exception' (fixes #2412, merged 2019-05-29, milestone 1.0, commit b49a6c3). A regression was fixed by PR #7020 'Restore behavior of the raises-exception cell tag' (closes #7015, merged 2019-08-16, commit 7d0b0528). Tested in the browser: with the tag, Run All continued past 1/0 to the last cell; without it, Run All stopped (the later cells kept count null), in both JupyterLab 4.6.4 and Notebook 7.6.3. Classic Notebook 6.5.x notebook/static/notebook/js/codecell.js:340 does the same. VS Code: microsoft/vscode-jupyter src/kernels/execution/cellExecutionQueue.ts:246-256 sets cellErrorsAllowed when the tags include 'raises-exception' (source read, not run).
  - Impact: Outside Colab, the tag alone already makes Run All continue, so a Run All that stops is a Colab-specific problem. Colab is said to ignore the tag; that is not verified here.
- **Q1-d** [verified]: In JupyterLab and Notebook 7, Run All continues past a cell that shows a red traceback but returns execute_reply status 'ok' (run_code catching the error and calling showtraceback), with no tag needed.
  - Evidence: Browser test of lastcell.ipynb in JupyterLab 4.6.4: run_code("""x = 5\nif x = 5:...""") and run_code("""print(1/0)""") were untagged and their errors were caught and shown with get_ipython().showtraceback(). Run All produced error outputs SyntaxError and ZeroDivisionError and still ran the last code cell (count 4). Source: packages/notebook/src/cellexecutor.ts treats reply.content.status==='ok' as success.
  - Impact: The catch-and-showtraceback form of run_code works in JupyterLab and Notebook 7 as well as in nbclient.
- **Q1-e** [verified]: In JupyterLab, pressing Shift+Enter (run-cell-and-select-next) on a collapsed heading moves the active cell to the first hidden cell, which expands the section. Arrow-down navigation skips collapsed sections instead.
  - Evidence: Headless test on JupyterLab 4.6.4 (browser/lab_test2_output.txt). With the collapsed '### Answer' heading active, notebook:run-cell-and-select-next made activeCellIndex 4 and the section came out collapsed:false, hidden:false, without running the answer cell.   - Impact: A student who steps through the page with Shift+Enter in JupyterLab opens each Answer when they reach it. If they ran Run All first, the live output is revealed at that point. Colab's behavior here is unknown.
- **Q1-f** [strong-evidence]: VS Code ignores jp-MarkdownHeadingCollapsed. Its notebook folding state is per-editor view state and is not stored in the .ipynb, so a notebook saved with collapsed Answer sections opens fully expanded in VS Code, and after Run All the answers and outputs are visible.
  - Evidence: microsoft/vscode at d2a9268 (2026-10-08): extensions/ipynb/src has no collapse, source_hidden or outputs_hidden handling outside tests. Folding is saved in INotebookEditorViewState.hiddenFoldingRanges (src/vs/workbench/contrib/notebook/browser/notebookBrowser.ts:430), which is workbench view state. Source read only, not run.
  - Impact: The collapsed-heading approach hides nothing in VS Code. That is acceptable only if the course targets Colab and JupyterLab.
- **Q1-g** [strong-evidence]: Plain JupyterLab 4.6 has no editor linting, so it shows no squiggles; the run_code string trick is needed only for Colab (and VS Code with Pylance).
  - Evidence: jupyterlab v4.6.4 packages/codemirror/package.json lists no @codemirror/lint dependency. When the server started, the log listed language servers as 'Skipped non-installed server(s): ... pyright ...', so LSP needs extra installs. No editor was screenshotted while typing.
  - Impact: Hiding errors from the editor is a Colab and VS Code concern.
- **Q2-a** [verified]: Catching the exception inside run_code and calling get_ipython().showtraceback() produces an 'error' output (ename, evalue, red ANSI traceback) while execute_reply status is 'ok'. nbclient with allow_errors=False runs to the last cell. - **Q2-b** [verified]: A SyntaxError looks different when raised normally than when raised through exec plus showtraceback. On IPython 9, a normal cell shows '  Cell In[3], line 2 / if x = 5: / ^ / SyntaxError: invalid syntax. Maybe you meant '==' or ':=' instead of '='?'.   - Evidence: Cells A_normal_syntax, run_show_syntax and run_plain_syntax in q2/py313/q2_outputs.txt and q2/ipy7/q2_outputs.txt. IPython 9.17.1 interactiveshell.py:2245-2248 sends SyntaxError to showsyntaxerror.

- **Q2-c** [verified]: For runtime errors, whether the run_code frame shows depends on the IPython version. - **Q2-d** [verified]: Calling get_ipython().run_cell(code, store_history=False) inside run_code makes errors look exactly like a normal cell's error on both IPython 7.34 and 9.17, with status 'ok'.
