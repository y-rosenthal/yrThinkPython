# research:colab

I could not reach colab.research.google.com from this container, so none of this was tested in live Colab. The facts come from three kinds of evidence: real Colab-saved .ipynb files on GitHub; Google's own course notebooks that students open in Colab straight from GitHub; Colab's open-source runtime code (googlecolab/colabtools) and copies of its release notes. I also ran local tests with Pyright 1.1.414 and nbclient/ipykernel.

Q1, saving collapsed sections: Colab saves collapsed heading sections in notebook metadata as metadata.colab.collapsed_sections, a list of cell ids. Each id belongs to the markdown heading cell. Colab-saved files keep that id in cell.metadata.id. When an nbformat 4.5 notebook already has top-level cell ids, Colab reuses them as its own ids and writes them back into metadata.id.

Q1, opening from GitHub: notebooks opened through colab.research.google.com/github/... do open with those sections collapsed. Google's ML Crash Course uses exactly this to hide "### Solution" sections that contain code cells. The gromacs-on-colab notebooks do the same and tell users to click "↳ cells hidden".

Q2, Run all and collapsed sections: Run all runs the cells inside collapsed sections; gromacs collapses its Input and Installation sections and still tells users to use Runtime -> Run all. A collapsed section hides its whole cells, outputs included, behind a "↳ N cells hidden" row with a run button.

Q3, errors and Run all: Run all stops at an error. That is the professor's own observation plus one forum post; ipykernel also cancels queued requests when a reply has status "error". Colab has no cell-tag UI, and I found no sign that it honors raises-exception.

Q3, showtraceback: Colab's Shell._showtraceback, like ipykernel's, sends an iopub "error" message. So run_code plus showtraceback() produces an error-type output while the reply status is "ok". Whether Colab's Run all also stops on error-type outputs is UNKNOWN. A fallback avoids the question: print the ANSI-colored traceback to stderr. I tested it locally; it produces only a stderr stream output, and nbclient runs to the end.

Q4, the squiggles: Colab's editor is Monaco. The diagnostics come from Pyright, running on the runtime VM as "/usr/colab/bin/language_service ... node /datalab/web/pyright/pyright-langserver.js". The setting is per user: Tools > Settings > Editor > Code diagnostics. One option is "Syntax and type checking", and by default type checking is off; I could not confirm the other option names. I found no per-notebook switch.

Q4, strings and ignore comments: Pyright does not look inside string literals (verified). In plain Pyright, a top-of-file "# type: ignore" silences every diagnostic, syntax errors included. A line-level "# type: ignore" or "# pyright: ignore" does the same for that line. Whether Colab passes these comments through, and whether it treats each cell as its own file, is unknown.

Q4, cell magics: before July 2022 Colab ran %%writefile bodies through the checker; a fix for "some magics" followed. Unknown or custom %%magic cells show as plain uncolored text, so a custom-magic question cell would lose syntax colors just like a string. Upstream Pyright's notebook mode would treat a whole %%magic cell as a comment, but I can't tell whether Colab uses that mode.

Q5, details and forms: markdown <details> works. A form cell ('#@title ... { display-mode: "form" }') hides only the code, and the output still shows. Google's own notebooks rely on the title directive alone, without cellView metadata. The 2026 UI also added a per-cell output collapse arrow; whether it is saved in the file or read from metadata is unknown.

Q6, headings: sections exist for markdown cells that start with a heading, at levels ##, ### and #### (seen); a leading blank line or text after the heading is fine. A section ends at the next heading of the same or higher level, so lower headings nest inside it. Down-arrow navigation has been reported to expand collapsed sections.

Most important things to test in real Colab before committing: (a) Run all past a run_code cell that calls showtraceback(); (b) whether collapsed_sections pointing only at top-level ids works (adding a matching metadata.id makes it safe); (c) what a custom %%magic cell looks like and whether it gets squiggles; (d) whether Run all, Shift+Enter or an error expands a collapsed Answer section; (e) whether "# type: ignore" at the top of a cell silences squiggles in Colab.

## Findings

- **Q1-format** [verified]: Colab saves collapsed heading sections as notebook-level metadata.colab.collapsed_sections: a JSON list of cell-id strings. Each id is the id of a markdown HEADING cell, and for Colab-saved files it is the cell's metadata.id.
  - Evidence: Real Colab-saved files from GitHub, inspected with a script. arnaldog12/Machine_Learning SVM.ipynb has "colab": {"provenance": [], "collapsed_sections": ["6UqxCLJdchUG"], "toc_visible": true, ...}, and cell #4 is a markdown cell with metadata {"id": "6UqxCLJdchUG"} and source '# 🔍 1. Introdução'. rickiepark/hg-mldl 3-1.ipynb has ["pLW8kdDv5asl"], which is the '## 과대적합 vs 과소적합' cell. multimodalart/majesty-diffusion v.ipynb has three ids pointing at '## Setup stuff', '## More setup stuff' and '### Advanced settings'. lorenlugosch/pytorch_HMM HMM.ipynb points at '#### ...' cells. In all of these the id matched a markdown cell's metadata.id; no file used a top-level id. Downloaded copies are in scratchpad/ultra/colab-facts/dl/.
  - Impact: To ship a notebook with Answer sections collapsed, write metadata.colab.collapsed_sections with the ids of the Answer heading cells.
- **Q1-ids-nbformat45** [strong-evidence]: When Colab opens an nbformat 4.5 notebook whose cells have top-level "id" fields, it reuses those values as its own cell ids. On save it keeps the top-level id and nbformat_minor 5, and writes the same value into metadata.id. A cell Colab adds itself gets only metadata.id. collapsed_sections can therefore contain the Jupyter-style ids.
  - Evidence: BATUTO90/BatutoDream-promt2 Copia_de_Colaboratory_Release_Notes.ipynb is a Colab 'Save a copy in GitHub' file: it has the inserted badge cell with metadata.id 'view-in-github' and colab.include_colab_link true. It still has nbformat_minor 5, and in 53 of 53 cells the top-level id equals metadata.id, e.g. "id": "064d2137", "metadata": {"id": "064d2137"}. The badge cell Colab inserted has no top-level id. In lambdamai/datascience ds/Pandas_1.ipynb, collapsed_sections is ["36396f4c"], a Jupyter-style 8-hex id, on the '## Датафреймы' cell, which has both "id": "36396f4c" and metadata {"id": "36396f4c"}. Not tested live: a notebook with only top-level ids plus collapsed_sections.
  - Impact: The repo notebooks have top-level ids only, with empty cell metadata. The safest form is collapsed_sections listing the Answer heading's id AND that same id copied into the heading cell's metadata.id, which is exactly what Colab itself writes. check_notebooks/review tools may need to allow metadata.id.
- **Q1-github-open-collapsed** [strong-evidence]: A notebook opened from GitHub (colab.research.google.com/github/...) with collapsed_sections opens with those sections collapsed. Google's own course material depends on this to hide solution sections that contain code cells.
  - Evidence: google/eng-edu ML Crash Course notebooks are linked as https://colab.research.google.com/github/google/eng-edu/blob/main/ml/cc/exercises/<name>.ipynb; the repo's own notebooks contain these links. ml/cc/exercises/intro_to_ml_fairness.ipynb has collapsed_sections listing three '### Solution\n\nClick below for some insights we uncovered.' heading cells. ml/cc/prework/intro_to_pandas.ipynb collapses '### Solution\n\nClick below for a solution.', and the next cell is the solution CODE cell (cities['Is wide and has saint name'] = ...) before '## Indexes'. bioinfkaustin/gromacs-on-colab's README links via colab.research.google.com/github/...; its notebooks collapse '#### Documentation' with the text 'Please click ***↳ cells hidden*** below to show the documentation'. googlecolab/colabtools issue #438 (2019): 'I can get sections to start collapsed by editing the "collapsed_sections" metadata in the raw ipynb file'. Colab itself was not reachable, so not personally observed.
  - Impact: The professor's idea (question as markdown, then a collapsed Answer heading section holding the live code cell) uses a mechanism Colab supports and Google itself uses for solutions.
- **Q1-saved-state** [strong-evidence]: Colab saves the collapsed state when it writes the notebook to Drive or GitHub. It keeps no separate per-user state, and with a local runtime the state was reported not to be saved.
  - Evidence: googlecolab/colabtools #4162 (2023): 'Considering a notebook connected to the local runtime, the information about collapsed cells is not saved ... the collapsed cells are those that were collapsed last time I was connected to a hosted runtime.' #438 says the collapsed state cannot be edited except through the UI or raw JSON.
  - Impact: A student who opens from GitHub, expands an answer, and saves a copy to Drive will save it expanded. That is harmless; the GitHub source keeps the collapsed default.
- **Q2-run-all-collapsed** [strong-evidence]: Run all executes code cells inside collapsed sections.
  - Evidence: bioinfkaustin/gromacs-on-colab GROMACS_for_production.ipynb collapses the '#### Input' section (a %%bash code cell) and '#### Installation' (code cells), yet its form tells users: 'After filling in this form, run the notebook by clicking *Runtime -> Run all* in the toolbar.' Issue #2990 (2022): to run one section, users 'collapse the section and click the run button by the "N cells hidden" message'. Not personally tested.
  - Impact: Run all will execute the answer cells hidden in collapsed Answer sections, which is what the professor wants.
- **Q2-outputs-hidden** [strong-evidence]: A collapsed section hides its entire cells, outputs included, and shows only the heading plus a '↳ N cells hidden' row. Outputs become visible when the section is expanded.
  - Evidence: #2990: the user wants to 'run the section without collapsing the cells (to see the progress/results on that section)', which implies results are hidden while collapsed. technion046195/semester_2019_winter homework_0_solution.ipynb: 'some sections might be hidden (collapsed), showing only the title of the section with a "↳ # cells hidden" note beneath it ... expand all the sections ... pressing Ctrl+[ or by clicking on all the "↳ # cells hidden" lines.' cdefinnda course notebooks: 'Make sure ... you don't have any cells hidden by uncollapse[d] section headings' before printing.
  - Impact: Live output (prints, tracebacks, turtle drawings) produced by Run all stays out of sight until the student clicks the Answer section open.
- **Q2-auto-expand-risk** [believed]: Moving the selection with the keyboard into a collapsed section (Down-arrow, and probably Shift+Enter moving to the next cell) has been reported to expand it. Whether Run all, a running cell or an error output inside a collapsed section auto-expands or scrolls to it is unknown.
  - Evidence: googlecolab/colabtools #171 (2018, closed, resolution not visible): 'Collapsed sections currently expand when down-arrowing over them.' I found nothing about expansion during Run all.
  - Impact: Must test in real Colab: Run all, and Shift+Enter through the question cell into the Answer heading. If Shift+Enter expands the section, students moving cell by cell may reveal answers by accident.
- **Q3-run-all-stops** [strong-evidence]: Colab's Run all stops at the first cell whose execution fails.
  - Evidence: The professor's own observation (problem statement #1). A fast.ai forum user: 'the runall option in the RUNTIME menu ... runs all the cells until it gets to the end or finds an error.' On the kernel side, ipykernel kernelbase.py line 925 reads 'if not silent and reply_msg["content"]["status"] == "error" and stop_on_error: await self._abort_queues()', and Colab's Kernel subclasses ipykernel.IPythonKernel (colabtools google/colab/_kernel.py).
  - Impact: Any answer cell that lets an exception escape will stop Run all.
- **Q3-raises-exception** [believed]: Colab does not honor the 'raises-exception' cell tag. It has no UI for cell tags.
  - Evidence: No Colab documentation, release note (2022-2026 copies checked) or issue mentions cell tags or raises-exception. The tag is an nbsphinx/MyST/nbclient convention, and the professor observed Run all stopping on tagged cells.
  - Impact: Keep the tag for nbclient and the website, but don't rely on it in Colab.
- **Q3-showtraceback-colab** [unknown]: In Colab, run_code(...) that catches the exception and calls get_ipython().showtraceback() produces an iopub 'error' message, which shows as a red traceback output, while the execute_reply status stays 'ok', so ipykernel does not cancel the queue. Whether Colab's FRONTEND also stops Run all on an error-type output is unknown.
  - Evidence: colabtools google/colab/_shell.py: Shell._showtraceback builds exc_content {traceback, ename, evalue} and calls self._send_error, which does session.send(..., 'error', ...), the same as upstream ipykernel zmqshell. I tested locally with nbclient and allow_errors=False (scratchpad/ultra/colab-facts/nbtest/): run_code with showtraceback gave outputs [('error', NameError)] and [('error', SyntaxError)], and the final print cell still ran.
  - Impact: Highest-priority live test: in Colab, Run all over a notebook with a run_code/showtraceback cell followed by print('end').
- **Q3-stream-fallback** [verified]: An alternative run_code prints the formatted ANSI-colored traceback to stderr: ip.InteractiveTB.stb2text(ip.InteractiveTB.structured_traceback(*sys.exc_info())). It produces only a 'stream' output, with no 'error' output and status 'ok', so no frontend or kernel error logic can stop Run all.
  - Evidence: Local nbclient run (scratchpad/ultra/colab-facts/nbtest/mk.py, t.ipynb): output [('stream','stderr')] whose text starts with '\x1b[31m-----...NameError...Traceback'. Colab renders ANSI colors in stream output (believed, not tested in Colab).
  - Impact: A safe fallback if Colab turns out to stop on error outputs. The traceback text is the same, so check_review's exact-output comparison can be kept.
- **Q4-engine** [strong-evidence]: Colab's code diagnostics come from Pyright running on the runtime VM, wrapped by Colab's language_service proxy. The editor is Monaco. Diagnostics therefore presumably need a connected runtime.
  - Evidence: ps -ef output saved in catafest/colab_google catafest_041.ipynb: '/usr/colab/bin/language_service --language_services_request_root_url=http://172.28.0.1:8013/ ... -- node /datalab/web/pyright/pyright-langserver.js --stdio'. Colab VM environment dumps in several repos show COLAB_LANGUAGE_SERVER_PROXY_LSP_DIRS=/datalab/web/pyright/typeshed-fallback/stdlib,... colabtools #4537 hover text: 'Cannot access member "to" for type "int" ... (reportGeneralTypeIssues)', a Pyright rule name. Release notes 2022-01-28: 'Python LSP support for better completions and code diagnostics. This can be configured in the Editor Settings (Tools → Settings)'. A later release note mentions 'dark editor themes for Monaco'.
  - Impact: The squiggles follow Pyright's rules. Code inside string literals and markdown cells is not checked.
- **Q4-setting** [strong-evidence]: The user setting is Tools > Settings > Editor > 'Code diagnostics', a dropdown that includes 'Syntax and type checking'. By default type checking is off. I could not confirm the other option names, presumably something like none or syntax only. The setting is per user, not per notebook, and I found no notebook metadata that controls it.
  - Evidence: Course notebooks on GitHub: ubsuny/PHY386 2025/HW/HW4.ipynb ('Google Colab has a built-in type checker (Pyright) ... Tools ... Settings ... Editor tab ... Scroll down to **Code diagnostics** and select **Syntax and type checking**'). panaversity/learn-agentic-ai: 'Tools > Setting > Editor > (scroll to the bottom) Code diagnostics and choose Syntax and type checking'. jbpost2/ST-554 says the same. colabtools #2635 is titled 'enabling syntax and type checking gives red line on valid code'. A Zenn article (Sept 2025, seen only as a search snippet; zenn.dev is blocked here) says type checking is not performed by default.
  - Impact: Students on defaults probably see only syntax-error squiggles. Undefined names and wrong calls are probably flagged only if a student turned on type checking. Hiding syntax errors from the editor matters most.
- **Q4-strings-markdown** [verified]: Pyright reports nothing for code inside string literals, e.g. run_code("""print('hello'\n""") or run_code("""len(1, 2, 3)"""). Markdown cells are not sent to the Python checker.
  - Evidence: Local Pyright 1.1.414 CLI on scratchpad/ultra/colab-facts/pyr/a_string.py: '0 errors, 0 warnings'. Markdown not being checked is believed rather than tested in Colab; Pyright only receives code cells.
  - Impact: Question code shown in markdown, or passed as a string, will never get squiggles.
- **Q4-ignore-comments** [verified]: In Pyright, a '# type: ignore' comment before the first statement of a file (other comments may come before it) suppresses ALL diagnostics in that file, syntax errors included. A line-level '# type: ignore' or '# pyright: ignore' suppresses that line's diagnostics, syntax errors included (e.g. 'if x = 3:  # type: ignore'). '# pyright: basic' does not suppress undefined names. Whether Colab passes these through (enableTypeIgnoreComments) and whether a cell counts as a 'file' is unknown.
  - Evidence: Local Pyright 1.1.414 tests in scratchpad/ultra/colab-facts/pyr/. Without comments (h_nocomment.py) there are 3 errors: 'Expected ":"', '"(" was not closed', 'Expected expression'. With line ignores (f_syntax_line.py) and with a file-top '# type: ignore' (g_file_ignore.py, i_second_line.py): 0 errors. With '# type: ignore' after a statement (j_after_stmt.py) the syntax error remains. Pyright's tokenizer source sets _typeIgnoreAll only when no tokens precede the comment. OSS pyright-langserver opens documents with IPythonMode.None, so one-document-per-cell vs concatenation depends on Colab's undocumented language_service.
  - Impact: A uniform first line '# type: ignore' in every question code cell might hide squiggles in Colab without giving anything away, if Colab treats each cell as its own document. Must test in Colab. A line-level ignore would mark the error line and give the answer away.
- **Q4-cell-magics** [strong-evidence]: Colab's checker has handled cell magics case by case. In 2022 it checked %%writefile bodies as Python; a fix for 'some magics' followed. Cells starting with an unknown or custom %%magic are shown as plain uncolored text. Whether a custom %%magic body gets diagnostics today is unknown.
  - Evidence: colabtools #2859 (2022-06): 'the syntax checker tries to parse %%writefile cells as Python code ... many red/yellow lines'. Release note 2022-07-01: 'Improve LSP handling of some magics, esp. %%writefile'. #4123 (2023-11): '%%python works, but is not highlighted (appearing the same as regular text)', fixed in release note 2023-11-27 'Added highlighting for the %%python cell magic'. #216 (2018): asks how to add highlighting for 'my own custom %%magic'. #5620 (2025): %%perl has no highlighting. Upstream Pyright's notebook mode (tokenizer.ts _handleIPythonMagics) would turn an entire %%-cell into one comment, but Colab's use of that mode is unconfirmed.
  - Impact: A custom %%question magic would display the question code without syntax colors, the same drawback as option B's string. It is not a better DRY option unless a Colab test shows colored code and no squiggles.
- **Q5-details** [verified]: Colab renders markdown <details><summary> as a working collapsible.
  - Evidence: The professor's screenshot (task context), and the current review pages already use it in Colab.
  - Impact: Static expected-output answers inside <details> keep working; they just can't contain a code cell.
- **Q5-forms** [strong-evidence]: A form cell such as '# @title Answer { display-mode: "form" }' loads with its code hidden. It shows the title and a 'Show code' link, and the cellView metadata is optional because Colab adds "cellView": "form" when saving. Forms hide only CODE: output is always shown below the form, and no form mode hides output.
  - Evidence: Copy of Colab's Forms doc (Bhavleenk/Colab-Guide Forms.ipynb): '# Hiding code ... You can see both code and the form, just the form, or just the code.' Its demo cell '# @title Click `Show code` in the code cell. { display-mode: "form" }' has metadata only {"id": ...}. Google MLCC numerical_data_bad_values.ipynb uses '# @title Task 5: Solution (expand this code block to view) { display-mode: "form" }' with no cellView metadata. Colab-saved files (majesty-diffusion, eng-edu) contain "cellView": "form". colabtools #2154 mentions the 'show code hyperlink below hidden code cells'.
  - Impact: A form cell alone does not solve the problem: after Run all its output would be visible. It could hide the answer cell's code inside a collapsed Answer section (cosmetic), and hidden code shows no visible squiggles.
- **Q5-output-toggle-2026** [believed]: Colab's 2026 UI has a per-cell output collapse toggle (a chevron on the left of the cell). It is unknown whether this state is saved in the .ipynb, whether Colab reads any metadata such as jupyter.outputs_hidden or collapsed on load, and whether new outputs from Run all stay collapsed.
  - Evidence: colabtools #5977 (2026-05-11): 'clicking the output dropdown toggle (the small arrow/chevron button on the left side of the cell) ... the arrow points downward when output is visible and rotates sideways (collapsed) when output is hidden.' Release note 2026-01-20: 'Launched a new modern design for the Colab UI.'
  - Impact: Worth one Colab test. If outputs_hidden metadata were honored and survived re-execution, it would be a simpler alternative, but this is unlikely and unproven.
- **Q6-heading-sections** [strong-evidence]: Collapsible sections come from markdown cells that start with a heading. Seen collapsed at levels ##, ### and ####; ##### headings appear nested inside a #### section; h5/h6 as section owners were not seen. The heading may be preceded by a blank line and followed by more text in the same cell. A section extends to the next heading of the same or higher level, so lower-level headings nest inside it. Collapsed sections show a '↳ N cells hidden' row with a run button.
  - Evidence: pytorch_HMM: a collapsed cell's source starts '\n#### *Why?*\nWhy might we care...'. eng-edu: collapsed '### Solution\n\nClick below for a solution.' followed by a code cell and then '## Indexes'. gromacs: collapsed '#### Documentation' followed by '##### License' and '##### About this software', which belong to that section according to its instructions. #2990, the technion notebook and the gromacs text quote '↳ cells hidden' / 'N cells hidden'. Release note 2023-07-21: 'Added a menu to the table of contents to support running a section or collapsing/expanding sections'.
  - Impact: An Answer heading one level below the question heading (e.g. '#### Answer' under '### Question N') ends at the next question. Answer content must not contain headings at #### level or above, or the section ends early. Colab's own table-of-contents sidebar will list every Answer heading (cosmetic).
- **Q6-colab-ui-change** [verified]: Colab launched a redesigned UI in January 2026 and moved some features since, so exact labels and placement ('↳ N cells hidden', the settings dialog) may differ from the 2018-2025 evidence.
  - Evidence: Mirrored release notes (MdShajalalsojib/Gub_project Colaboratory_Release_Notes.ipynb), 2026-01-20: 'Launched a new modern design for the Colab UI.'
  - Impact: Treat the UI wording as approximate. A single live Colab session should confirm the plan before rolling it out to six notebooks.
